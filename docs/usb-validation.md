# USB安定化の検証

Roadmap #4 のP0に対応する。自動テストで確認したソフトウェアの挙動と、実物で確認が必要な項目を分けて記録する。USB印刷は引き続き`--experimental-usb`、観測済み24mmカートリッジ、1枚、内容長100mm以下に限定する。

## ソフトウェアの検証

- シリアルとVID/PIDが同じならbus/addressが変わっても選択できる。重複シリアルは拒否する。`usb:sr-mk2`は該当機種が1台のときだけ選択する。
- 疑似transportでヘッダー、1024行ごとのラスタ、form feed、resetの順序を検査する。部分転送、切断、不正・短い応答、機器エラーで後続送信と再送が止まることを確認する。
- 完了待ちに入る前のbusyは完了根拠にしない。完了待ちでST=1/2を観測してからST=0、ER=0へ戻った場合だけ成功する。idleのみ、ST=3/4/5のみでは期限切れになる。
- 中断時の送信有無と処理段階を保持する。送信前はnot_submitted、送信後の中断・通信障害はunknown。結果JSONと永続記録の識別子・エラー内容を照合する。
- statusは既知の状態と観測済みカートリッジの一致を表示する。未知の値をカバー開・テープなしなどの原因へ推測変換しない。

疑似応答は制御フローを検証するための合成データであり、実機の異常応答を採取したfixtureではない。実機で観測した通常時の22バイトと完了時ST `[2,0]` の根拠は[USB調査](usb-protocol.md)にある。

## 実機確認の手順

2026-11-10の初期実装では50mm指定の校正ラベルを印刷し、自動カットとCLIの正常終了を確認済み。正確な物理寸法、各異常状態、新しいシリアル選択経路の実機確認は未実施。今回の作業開始時点ではUSB一覧に機器がなかったため、追加の実機印刷は行っていない。

各試行で、OS、CLI commit、本体/firmware情報（不明なら不明）、カートリッジ品番・幅、接続方法、電源、job ID、attempt ID、statusの生値を残す。試行記録の保存先はCLI結果の`record_path`にある。

1. 電源・24mmテープ・USB接続を準備し、`tepra devices --json`で対象を確認する。`preferred_selector`を使い、`doctor`と`status`を保存する。
2. USBを接続し直して再列挙する。シリアルがある場合は同じシリアル指定で`status`が取れることを確認する。シリアルが取得できない場合はその旨を記録し、固定個体の再識別を検証済みとしない。
3. 下記の手順で10/50/75/100mmの校正ジョブを準備する。75mmは1063dot、100mmは1417dotで1024行の分割境界をまたぐ。まず短いジョブから1枚ずつ明示的に印刷する。
4. 左上の横長印・右下の縦長印、外枠の欠け、鏡像、5mmごとの目盛りを確認する。送り方向の外枠の長さ、ヘッド方向の幅、前後余白、カット後全長を定規で測り、プレビューとの差を記録する。指定長は描画領域であり、カット後全長ではない。
5. 別の試行として同じ条件を繰り返し、ジョブごとの印字・カット・CLI結果を照合する。結果不明になった場合、出力を確認してから次の試行を判断する。

```sh
# 75mmの例。ファイルは既存のものと別名にする。
cargo run --example calibration -- calibration-75.png 75
tepra render calibration-75.png --content-length-mm 75 \
  --output preview-75.png --job job-75.json --json
tepra print --job job-75.json --device usb:sr-mk2 \
  --experimental-usb --dry-run --json
# 実機で1枚印刷する操作
tepra print --job job-75.json --device usb:sr-mk2 \
  --experimental-usb --json
```

## 未実施の異常系

各条件を個別に作り、まず送信前のstatus/print結果を記録する。カバー開、テープなし、対応外テープ、電源なし、USB切断、他アプリ使用中の状態値と終了コードを確認する。状態の作成・解除は本体の通常操作に従う。

送信中のUSB切断・中断は、正常印刷が再現できてから別の試行で確認する。部分印字や残留ジョブがある可能性を記録し、復旧後に自動で再送されないこと、次の明示的なジョブの挙動を確認する。公式アプリとの競合も実測するまでは排他済みとしない。

これらの実機結果が揃うまでP0全体を完了扱いにせず、試験的フラグも解除しない。GitHub ActionsはLinuxのみで、実機への送信は行わない。
